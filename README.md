## 一句话

把「空间重建」从**可浏览**变成**可玩**：真实房间只用 3DGS 重建一次，
此后所有变化都来自 **Aholo Lux3D** 生成的 3D 内容。

## 为什么这样设计

评审权重里 **30% 是 Manycore 工具使用 + 25% 是好玩**。所以最优解不是做一个
炫技 demo，而是让**玩法本身离不开 AI 生成的 3D 物件** —— 没有 Lux3D 就没有游戏内容。

| 设计决策 | 原因 |
| --- | --- |
| **一间房，无限层** | 美术成本 = 一间房。变化的是物件，不是场景。完成度天然高。 |
| **异常由生成物件供给** | Lux3D 是内容引擎，不是贴图库 → 工具分是「核心」而非「点缀」。 |
| **没资产也能玩** | 每个物件都有程序化占位模型；GLB 到位后按 key 自动替换。**缺资产永远不是崩溃。** |
| **一眼可判的规则** | 不需要背房间、不需要和上一层对比 —— 这条约束砍掉了整类设计。 |

## 玩法

第一人称走进一间真实重建的公寓。它看起来就是一个普通的家 —— 问题恰恰在这里。

准星对准，左键标记。**标对不消耗任何东西**（剩余时间越多分越高），**标错才扣** ——
每次扣 8 秒，每层只有 3 次失手额度。用完这一层就结束，找齐则下潜一层。

### 一条规则，一眼可判

**标记任何不可能出现在一个家里的东西。**

这条约束不是修辞，它决定了哪些机制能用：

> 我们**删掉了**「东西消失了」这类异常。它只有在记得原样的前提下才成立，
> 而玩家第一次进房间时没有参照物。任何需要「和之前对比」的异常都不能用。

### 恐怖不在房间，在放进来的东西里

房间本身不吓人 —— 它是一间正常的公寓，这正是它可判的前提。恐怖全部来自
被放进去的东西，以及它们出现的方式：

四种惊吓，不是一种吓四次。闪一张脸 150 ms、同一张脸用 420 ms 慢慢逼近、
全黑 620 ms 并顺手掐掉手电筒、以及隔一拍再来一次的连环。**一个效果换六张脸仍然
只是一种惊吓** —— 学乖了的玩家不会再缩脖子，所以变的是事件的形状，不只是内容。
深层的楼层才会解锁后两种：还没学会路的玩家会把「全黑」读成 bug，而不是威胁。

黑暗 0.18 → 0.86、手电筒半径从屏幕短边 0.62 → 0.26、闪烁 0.25 → 1，都随层数递进。
手电筒是唯一的工具，所以它**可见地**变得不够用 —— 这比把房间调暗更有效。

### 唯一一种你能活下来的惊吓

上面四种都是**发生在你身上**的，像天气。第五种不是：从第 3 层起，有一部分惊吓会换成
**有东西从房间那头朝你过来**，窗口 2.2 秒（第 3 层）递减到 1.0 秒（第 8 层），
你要在这段时间里点鼠标把它打掉。

它不是 `ScareKind` 的一员，而是独立的一条线 —— 那四种由随机挑选、由计时器结束，
这个由**玩家**结束。混进那个列表，随机挑选迟早会挑中一个没人点击就永远不结束的事件。

窗口**不点中它本身，点哪都算**：东西已经占满屏幕、房间在变暗，这时候还要求精确命中
移动的像素，考的是鼠标不是胆量。失败的是错过窗口，不是错过那一个像素。
打掉只给一句「解除」，不给分数 —— 它让玩家觉得自己**能做事**，而不是给它发奖励。

### 主画面与暂停

进入游戏前有主画面（开始游戏 / 操作说明 / 画质），游戏中按 Esc 暂停，
暂停页有「回到游戏」「回主画面」和画质开关。

暂停是靠**鼠标锁丢失**驱动的，不是靠监听 Esc：Esc 是浏览器的键，它负责退出指针锁定，
而且不保证把 keydown 送进页面。锁丢了这件事总会到达，而且意思永远是同一个。

### 流畅度：一个假设被推翻，一个被**重新证实**

你排第一的是流畅度，所以我把它当成测量问题。这期间我犯过一次错，也纠正过一次，两件事都留在这里，因为纠正比结论更有说服力。

**先说被推翻的那个。** 为了省帧时间我加了 `sort.minIntervalMs`，限制高斯点排序多久最多跑一次，理由是「瓶颈在 CPU 排序」。`npm run bench:sort` 用 335 帧、四个设置测下来：

| 排序间隔 | 每帧中位 |
|---|---|
| 0 ms（每帧排） | 2134 ms |
| 8 ms | 2072 ms |
| 24 ms | 2052 ms |
| 50 ms | 2088 ms |

**2–4%，全在噪声里**，而且原因是结构性的：

> 这个选项限制的是「多久最多排序一次」，可渲染器本来就**每帧排一次**。在慢到需要帮助的机器上帧长远长于任何合理间隔 —— 0.5 fps 时帧长 2000 ms，24 ms 的上限**永远不会生效**。它只在帧率高于 1/间隔时才起作用，而那正是**不需要它**的机器。

它被**移除了**。一个什么都不做的画质旋钮比没有旋钮更糟：它花掉配置、测试，还让人以为性能问题已经处理过了。

**再说被纠正的那个 —— 而且它原来是我自己写错的。** 我一度写下「瓶颈不在填充率，因为 640×360 并不比 960×540 快」。那个判断是用**不可靠的方法**测的（每档只采到几帧就下结论）。用后来这套方法（每档 90 秒、同机同视角同种子、钉住相机）重测：

| 条件 | 每帧中位 | 说明 |
|---|---|---|
| 1.00× + 渲染重建 | 2017 ms | 满分辨率 |
| 0.55× + 渲染重建 | 1400 ms | 省掉 31% |
| 0.40× + 渲染重建 | 1333 ms | 省掉 34% |
| 1.00× **关闭重建** | **17 ms** | 帧的其余部分 |
| 0.40× **关闭重建** | **17 ms** | 与分辨率无关 |

三个结论，都是量出来的：

1. **重建占 99% 的帧时间**（2017 ms → 17 ms）。时间确实花在 splat 上；
2. **分辨率是有用的杠杆：0.40× 省掉 34%。** 我先前那条「填充率不是瓶颈」的结论**是错的**；
3. 除重建之外，整帧只要 **17 ms（约 59 fps）** —— 引擎、合成、我自己的每帧代码都不是问题。

顺带得到一个设计确认：0.55× 已经拿到 31%，而 0.40× 只再多 5%。**收益在 0.55 附近就基本吃完了**，所以把 0.40 当下限是对的，再往下只是糊画面。

**还有一件从这张表里掉出来的事。** 表里 1.00× 是 2017 ms —— 一帧两秒。控制器的规则是「连续两次读数同向才动手，每次动一档」，五个档位就是**二十秒的幻灯片**，而玩家通常在那之前就关掉了。所以当帧率低于目标值的四分之一时，它**一次让两档**（`PANIC_FPS`）：对一台差得很远的机器，谨慎的代价是玩家的头半分钟。防抖没有变 —— 仍然要连续两次读数，因为单帧卡顿是楼层在加载，不是对机器的判决。这两件事都有单测，包括**「只是有点慢」时不许触发**这一条。

### 一个只有分享链接才会暴露的 bug

写这轮的质量快捷键时，验收报了一句很具体的话：**按键事件到了，但状态没变**。

原因是那个 `keydown` 监听器装在 `showMenu()` 里面，而 `showMenu()` 只在**不带 `?autostart=1`** 时才跑。也就是说：**所有 demo 链接里，F3 帧率、F 手电筒、数字键画质统统是死的** —— 而菜单页上它们都是好的。这类 bug 用眼睛测一百次也发现不了，因为你测的时候总是从菜单进去的。

现在 `installKeys()` 在 boot 时注册一次，和菜单位置无关。新增三条验收（`65/65`）全都读**画布尺寸**而不是读状态变量 —— 一个只改状态的控件不算控件。

### 那为什么线上还是卡？

因为这台机器用 **SwiftShader 软件光栅化**，1.00× 是 2017 ms/帧 —— 降 34% 之后仍是 1333 ms，救不回来。**绝对帧率在这里不具代表性**，它只说明「splat 光栅化是这类渲染器的成本中心」。

真正合法的问题只剩一个：**在你的显卡上，1.00× 是多少 fps？** 按 `F3` 会显示
`fps · 最慢 ms · 帧数 · 模型数 · 画质档位 · 分辨率`，**以及浏览器真正在用的那块 GPU 的名字**。

最后一项是新增的，因为它是唯一一条能一句话分流的分叉：如果那行写着
「⚠ 软件渲染（未用显卡）」，那么所有其他数字都不是在测量这个游戏，而是在测量降级路径，
问题在浏览器/驱动侧而不在设置里；如果写着一块真实显卡的名字却仍然只有个位数帧率，
那才是设置问题。`WEBGL_debug_renderer_info` 是页面里唯一能看到真实适配器名的地方 ——
没有它，软件光栅化和一块没被用上的显卡从页面内部看起来完全一样。

这条诊断本身错了两次，两次都是**验收抓的，不是读代码看出来的**。

**一、截断把关键词切掉了。** 为了「适配一行」把名字按 `(` `,` `)` 切开取前缀，而
Chromium 报的是 `ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero) ...))` ——
前缀就是 `ANGLE`，里面没有任何「软件」的线索，于是**在唯一需要这条警告的机器上，
`isSoftwareRenderer()` 返回 false**。现在完整字符串单独保存，判据读完整的，
只有显示才截断。

**二、空答案被当成答案缓存了。** 页面第一次探测可能返回空串（上下文还没就绪、
扩展还没暴露），而缓存它会让 `isSoftwareRenderer()` **整局**都是 false。
验收的输出就是证据：`software=false (before=false)` —— 画菜单的那一刻为假，
紧接着就为真，也就是说警告**恰好在唯一一次显示它的调用上被跳过了**。
现在空串不缓存、下次重探。

第二条同时说明了停止条件为什么重要：这个 bug 不会让任何看起来该坏的东西坏掉，
它只是让那句警告安静地不出现 —— 如果没有「软件渲染时必须出现」这条断言，
它读起来和「这台机器是好的」完全一样。

### 四个旋钮假设，四个都错

先前猜「每帧的 CPU 排序是瓶颈」，于是测了 `sort.minIntervalMs` —— 无效。
后来又猜是排序的**精度**，于是测了 `sort.highPrecisionEnabled` 和
`pack.highPrecisionEnabled`。`tools/bench-splat-config.mjs` 在同一个房间里
一次只动一个。

第一轮跑出来的是这张表，当时写进了这份文档：

| 条件 | 帧时间 | 相对基线 |
| --- | --- | --- |
| 对照：隐藏重建 | 31 ms | — |
| 基线（全默认） | 1724 ms | — |
| `sort.highPrecisionEnabled=false` | 1709 ms | **−0.9%（无效）** |
| `pack.highPrecisionEnabled=false` | 1682 ms | **−2.4%（无效）** |
| `raster.maxPixelRadius=2` | 1357 ms | **−21%** |
| `raster.maxStdDev=1.5` | 1573 ms | −8.8% |
| `raster.detailCullingThreshold=0.02` | 1174 ms | **−32%** |

**这张表是错的，而它的错法比第一版的 77% 假结论更隐蔽。** 重跑（采样时间加倍、
并把「默认值」当作待测条件之一）之后：

| 条件 | 第一轮 | 重跑 | 帧数 |
| --- | --- | --- | --- |
| 基线（全默认） | 1724 ms | **1091 ms** | 21 |
| `raster.detailCullingThreshold=0.02` | 1174 ms（−32%） | **1662 ms（更慢）** | 17 |
| `raster.maxPixelRadius=2` | 1357 ms（−21%） | 1026 ms（−6%） | 22 |

基线自己就从 1724 ms 漂到 1091 ms —— 这个房间在软件光栅化下的噪声比任何
旋钮的效果都大。工具这次自己拒绝了结论：

    NO VERDICT: 6/10 conditions drew at least 20 frames and one of them was
    the baseline. Raising SAMPLE_MS is the fix; reading a ranking off the
    numbers above is not.

**四个假设全部落空，四个旋钮一个都没进代码。** 第一轮的表之所以看起来有结论，
是因为条件太少、每个条件只量了十几帧，而**「隐藏重建」这个对照只证明了房间在场，
没有证明任何两个条件之间的差是真的**。对照能挡住「量到了空场景」，
挡不住「把噪声当信号」—— 那是样本量的问题，不是对照的问题。

真正站得住的只有分辨率和它的一条实测曲线（`tools/bench-render.mjs`）：

| 条件 | 帧时间 |
| --- | --- |
| 1.00x，画 splats | 2057 ms |
| 0.55x，画 splats | 1529 ms（−26%） |
| 0.40x，画 splats | 1452 ms（−29%） |
| 1.00x，隐藏 splats | 25 ms |

**重建占了 99% 的帧时间**；分辨率是唯一可测的杠杆，而且 0.55x 已经拿到 0.40x
所能拿到的绝大部分。所以「0.40x 还卡」不是设置没调对，是分辨率这条路已经走完了 ——
剩下的只有「这台机器到底有没有在用显卡」，也就是 F3 那行的用途。

### 两个只有真实缺文件才会暴露的 bug

两个都是在把 55 个资产铺满目录的过程中，被验收而不是被阅读发现的。

**一、把网页当成了模型。** `loadAssets` 只检查 `response.ok`。静态托管对不存在的路径
会回 **200 + `index.html`**，于是那段 HTML 被当成 GLB 存进模型缓存，
加载器对 `<!doctype html>` 做 `JSON.parse`，**整局游戏崩掉** —— 只是因为少了一个文件。
现在校验 GLB 魔数（`glTF`），不是模型就按 404 处理。

**二、一个不返回的请求会卡死换层。** `SplatRoom` 里写着这个隐患却没修：

> retrying it on every floor was tried and hung the page (`await Promise.all` never
> settles when a fetch does not return), so the fix has to come with a timeout on the
> fetch itself

防重试的守卫加了，它要求的那个超时一直没写。连接建立后卡住的请求（断掉的移动网络
就是这样）会让 `loadAssets` 永不 settle，楼层串行链再也不前进：玩家看到上一层的横幅、
等不到下一层，没有报错也退不出去。现在每个资产请求带 20 秒的 deadline。

发现方式值得记下来：验收里那条「暂停后时钟应当停住」在 `floorClear` 里坐了三十秒，
而 `floorClear` 正常只存在 900 ms。

### 代码里的注释预言了这个 bug，然后它照样发生了

`plan` 的声明上方写着：

> Declared up here rather than next to `startFloor` because the autostart path calls
> `startFloor` *synchronously* from `main`, and a `let` declared further down is still in
> its temporal dead zone at that moment — which threw `Cannot access 'plan' before
> initialization` and broke every demo link. The menu path hid it, because a button
> handler runs after `main` has finished.

**两段注释、两个文件之外，我在同一份文件里又造了一个同类的 `let`。** 新的寻物提示要一个
`hintGiven` 标记，我把它写在了它被使用的位置旁边。于是：

```
?autostart=1  →  Cannot access 'hintGiven' before initialization  →  state = 'failed'
```

整个游戏起不来 —— 而**从菜单点进去完全正常**，因为按钮回调在 `main` 跑完之后才执行。
也就是说：**能测到的路径是好的，会被分享的那条是坏的。**

更值得记的是它为什么躲过了 71 条验收：

| 路径 | 结果 |
| --- | --- |
| `npm run dev` 后从菜单点「开始」 | ✅ 正常 |
| `?autostart=1&floor=3`（验收里唯一测过的 autostart） | ✅ 正常 |
| **`?autostart=1`（默认，也就是发给评委的链接）** | ❌ 白屏 |

崩溃只发生在 `floor === 1` 的那条分支里，而验收把 autostart 检查写成了 `floor=3`，
恰好绕开了唯一会崩的分支。现在多了一条**专门加载裸 `?autostart=1`** 的检查 ——
它在这个有 bug 的版本上是失败的。

### 一个能通过、但什么也没证明的检查

同一条暂停检查还犯了第二种错。它这样写：

```js
const a = s.timeLeft;
await new Promise((r) => setTimeout(r, 700));
const b = s.timeLeft;          // 期望 a === b
```

在这台机器上，重建场景的渲染速度**低于每秒一帧**。所以这 700 ms 里常常一帧都没有 ——
而时钟只在帧里走动。换句话说：**把暂停逻辑整个删掉，这条检查仍然会通过**，
因为根本没有东西在推动时钟。

这是这个项目一直用的那条原则的反面：**一个在什么都没工作时也能通过的检查，
比没有检查更糟**，因为它把「没测」伪装成「测过了」。

修法不是加长睡眠，而是让门变得可观测：把帧循环里那一行
（`if (debug.state === 'playing' && autoRender)`）抽成函数，帧循环调用它，
再用一个 debug 接口带着指定的 `dt` 调用同一个函数。现在检查是**手动走两次十秒** ——
暂停时一次、恢复后一次 —— 断言落在两次的差上。删掉暂停，它就红。

### 准星指着一个东西，就该算指着那个东西

`pick` 是一条光秃秃的 `raycaster.intersectObjects`。这是精确的，也是对的默认值 ——
但它让**标记一个东西的难度，取决于那个东西恰好在射线上有多少实体表面**。
目录里的植物、画像、人偶、吊着的人形，在它们包围盒中心基本都是空的。

于是验收里出现了 `onScreen=true` 紧挨着 `result=miss`：房间说准星在物体上，
标记说不在。第 1 层那个是**一盆植物**。

容差是**兜底而不是放宽**：只在射线**什么都没打到**时才生效。墙或无辜家具挡在前面时，
射线会打到它，精确答案照旧 —— 所以这不能用来隔墙标记，也不能越过一件家具去够后面的异常。
它只覆盖「准星确实压在一个真实物体上，而那个物体在被瞄的地方有个洞」。

### 「能通关」是量出来的，不是设计出来的

通关条件是第 8 层走完，有结局画面、有单测、有实机验收。但「存在一条赢的路径」
和「每一层都打得通」是两件事，只有后者是关于玩家的。第 8 层给 6 个异常、
114 秒、以及一支只照亮屏幕短边 27% 的手电筒 —— 在这之前，没有任何地方说过
那是一条硬关卡还是一条死路。

`npm run search:time` 测的就是搜索本身。人类找东西不是把准星射线对准它，
而是扫视房间、在它进入注意力范围时发现它。所以模型是：**视角方向与物体的夹角
小于「物体自身角半径 + 20° 余光带」就算被注意到**。这也是为什么用准星射线的
机器人在这里没有意义 —— 要求射线精确碰到一圈牙齿，会算出一个没人认得的数字。

| 层 | 要找 | 房间里的物体 | 限时 | 扫视一遍 | 剩余 |
|---|---|---|---|---|---|
| 1 | 1 | 1 | 240s | 6.1s | 233.9s |
| 3 | 3 | 3 | 204s | 14.6s | 189.4s |
| 5 | 4 | 10 | 168s | 20.7s | 147.3s |
| 8 | 6 | 12 | 114s | 21.1s | 92.9s |

「要找」和「物体」不是一回事：`twin` 是同一个异常的 3 份副本，共用一个槽位，
标记任意一份即可。第 5 层起解锁 `twin`，所以物体数从 3 跳到 10。

**最难的一层还剩 92.9 秒。** 这个数字是**下界** —— 它只算了看，没算走路、
没算判断一把普通椅子是否普通、也没算从一次失手里恢复。所以时间从来不是
这条游戏的瓶颈；8 层全部通过才算通过，任何一层扫不完就 exit 1。

### 房间必须先有「正常」，判断才有对象

「标记任何不可能出现在一个家里的东西」要求玩家知道**一个家应该有什么**。

第一版里，房间自己的摆设和异常都从同一份荒诞目录里抽 —— 橡皮鸭、交通锥、地精、
宇航员。无辜的和有罪的看起来是同一类东西，「这东西该不该在这儿」于是没有真值，
`intrude` 这个类型甚至因为无法判断而被删掉过。

现在房间里的旁观物件全部是**普通的家务家具**：盆栽、垃圾桶、椅子、落地灯、水壶……
13 个离线生成为扁平着色的 GLB，十三个加起来 **83 KB** —— 比原来一张 2048² 贴图还小。
它们什么都不做，它们**就是那个「正常」**。

于是判断变成两个互不相交的集合：

| 判断 | 内容 | 用的是什么 |
| --- | --- | --- |
| **它不该存在** | 房间里凭空多出来一个不是家具的玩意 | 只有 `intrude`，全是 Lux3D 生成物 |
| **它不该这样** | 同一个家具做了家具做不到的事 | 其余 6 种，全用家务家具 |

`foreignPool` 只排除 `weirdness === 0`，所以两个集合从任一侧都不可能重叠。
这把「该不该在这儿」从一个见仁见智的问题，变成了一个有唯一答案的问题。

这条分界**在三个地方被断言**：一个覆盖所有楼层的单测、一条读真实目录
（而不是读一份拷贝）的实机验收，以及关卡设计本身 —— 第 1 层只放一个漂浮的普通椅子，
教的就是这件事。

现有 7 种异常，全部满足这条规则：

| 类型 | 内容 | 载体 |
| --- | --- | --- |
| `intrude` | 凭空多了一件 AI 生成的东西 | **Lux3D 生成物** |
| `stare` | 一个东西悬在人的高度，**一直在看着你** | 家务家具 |
| `shift` | 东西浮在半空 / 被钉在天花板 | 家务家具 |
| `warp` | 尺寸或颜色被改了 | 家务家具 |
| `twin` | 同一个东西出现了 3–5 个 | 家务家具 |
| `invert` | 东西**倒挂**着，没有任何东西托着它 | 家务家具 |
| `swarm` | 同一个东西出现了十几个，数不清 | 家务家具 |

`stare` 在程序化房间（`classic.html`）里仍用恐怖资产 —— 那条路径没有家务家具，
改动只在真实房间这一侧。

### 两个渲染后端，一套玩法

| 后端 | 入口 | 说明 |
| --- | --- | --- |
| **真实房间** | `/`（默认） | `@manycore/aholo-viewer` 渲染官方开源 3DGS 场景，配官方体素碰撞场 |
| 程序化房间 | `/classic.html` | three.js 搭的同一套房间，用于对比与回退 |

两者共享 `src/game/`（规则、目录、类型）—— **那一层不含任何渲染依赖**，
所以同一套关卡生成逻辑被两个后端使用，也被全部单测覆盖。

```
src/
  game/            纯逻辑，不含 three.js
    types.ts       类型
    catalog.ts     程序化房间的真相：墙体、家具槽位、生成点、AI 异物定义
    rules.ts       种子随机、楼层生成、判定、计分
  viewer/
    VoxelCollision.ts  八叉树体素碰撞（取自 Aholo 官方示例，附出处）
    voxel.ts           胶囊体解算与坐标换算
  splat/           真实房间后端
    main.ts        循环、状态机、全部界面
    SplatScene.ts  viewer 配置 + splat 加载 + 体素场
    SplatPlayer.ts 第一人称手感（阻尼、蹲伏、头部摆动）
    SplatRoom.ts   异常摆放、注视者动画、拾取
    audio.ts       靠近异常的持续音 + 标记音
  aholo/client.ts  Aholo API 客户端（生成异物资产）
tools/             验收与构建工具（见下）
```

| `deploy:check:live` | 8 项，同上，但直接打线上 URL，并**确认这就是当前构建** |

### 两条贯穿始终的检查原则

**1 · 断言必须有两侧边界。** 「走不过去」和「根本没动」在数值上无法区分 ——
一个永远不动的行走者也能满足「没有走出房间」。所以碰撞检查同时断言：
有碰撞时走不远（8.36 m），**关掉碰撞后必须走得很远**（34.83 m）。

**2 · 对照是必需项，不是加分项。** 「异常朝向玩家」只有在
「地面物体**不**转头」也成立时才有意义 —— 否则整个房间一起转也会通过。

这套检查真的抓到过 bug，包括一个只有演示链接才会触发的崩溃：
`?autostart=1` 时 `let plan` 还在暂时性死区（菜单路径永远碰不到，因为按钮回调跑得晚）。

## Aholo 集成

- **Aholo Lux3D（必需）**：生成异物资产。prompt 写在 `data/foreign-assets.json`。
  **两条路，任选其一** —— 网页版不需要 API key：

  ```bash
  # 有 key：一条命令跑完 21 个（生成 → 轮询 → 下载 → 记录来源）
  npm run assets:generate

  # 没有 key：在 https://lux3d.aholo.ai/lux3d/home 用网页版逐个生成并下载，
  # 然后把下载目录交给这个工具，它会校验、命名、归位并记录来源
  npm run assets:import -- ~/Downloads
  ```

  `assets:import` 会交互式列出每个 key 对应的 prompt，你按着读就能对上；
  也可以用 `--order`（按目录顺序）或 `--set duck=file.glb`。

- **Aholo Viewer / 3DGS（已用）**：真实房间后端，见 `docs/05-3DGS接入配方.md`。
- **Aholo API（可选）**：`src/aholo/client.ts`，用于批量生成。

生成结果没有统一的比例和轴心，所以会按每个资产的目标高度归一化、
并把底面重新对齐到 y = 0 —— 否则「一盒牛奶」会以两米高进来。

`npm run assets:check` 会断言「哪些资产真的来自 Lux3D」。
**这不是多余的**：原先的判断只看 `.glb` 是否存在，而占位模型写在同样的路径上，
于是填上 key 之后工具会报「无事可做」并跳过全部 21 个 —— 静默失效。

## 部署

```bash
npm run deploy
```

先跑 `deploy:check` 验证构建产物在子路径下可运行，**通过后**才把 `dist/`
发布到 `gh-pages` 分支。GitHub Pages 从该分支提供服务。

Pages 是异步重建的，推送完站点还是旧的。等它跑完，再确认提交链接上跑的是
**这次构建**：

```bash
npm run deploy:check:live
```

这条会直接打开线上 URL 实测（8 项）。其中一项把线上 `index.html` 引用的
bundle 文件名和本地 `dist/` 比对 —— 因为「链接能用」和「链接是我刚验收的
那个东西」是两个不同的断言。**改了游戏、本地验收全绿、忘了重新部署**是一条
非常容易走上的路，而其他每一项都会照常通过：旧构建也能跑。

### 线上地址当前是 404，原因在仓库可见性

**`https://cyn-nya.github.io/foreign/` 返回 404，而 `gh-pages` 分支本身是好的。**
推送的树完整（`.nojekyll` / `assets/` / `index.html` / `classic.html`），
`deploy:check` 对着同一份产物跑是 **7/7 全绿**。所以问题不在构建，在托管：

    gh api repos/cyn-nya/foreign --jq '{private,has_pages}'
    → {"private":true,"has_pages":false}

**私有仓库不能开 GitHub Pages**（免费计划），所以这个地址从来就没能提供服务 ——
这也解释了为什么试玩一直是「从本地进去」。改可见性是仓库所有者的决定，
不是部署脚本能代劳的。要让线上地址生效：

```bash
gh repo edit cyn-nya/foreign --visibility public --accept-visibility-change-consequences
npm run deploy          # 重新推送，Pages 才会开始构建
npm run deploy:check:live
```

在那之前，本地就是唯一能跑 demo 的地方（`npm run dev`，需要联网取 63 MB 房间）。
`deploy:check:live` 会一直红着，而**它是唯一能发现这件事的检查** ——
`deploy:check` 验的是构建产物，构建产物没有问题。

> 不用 GitHub Actions 是因为 GitHub 不允许 OAuth app 在没有 `workflow`
> scope 的情况下推送 `.github/workflows/`。若要改用 Actions，见
> `docs/deploy/github-pages-workflow.yml` 顶部的说明。

## 已知限制

- **资产已全部由 Lux3D 生成完**：目录里 55 个资产，已生成 **55** 个（Lux3D 文生 3D），
  **0** 个仍是程序化占位，另有 **13** 件家务家具（就是"无辜"的那一半，同样走 Lux3D，
  因为它们混在实景重建里必须和房间一样写实）。
  缺任一个的情况下游戏都完整可玩 —— 缺文件时退回程序化几何体而不是崩掉，
  跑 `npm run assets:generate` 即可补齐，不改动任何玩法逻辑。

  上面这三个数字由 `npm run assets:check` **对着磁盘核对**。它们原先写错了两处：
  写的是「21 个程序化占位模型」，而 21 是**异物**的个数、不是占位的个数，
  真正还是占位的只有 7 个。这类数字只要靠手写就会腐坏，所以改成被断言的。

  传输层已经**对着真实接口验证过**：用一个故意无效的 key 调用只读的
  `task/list`，服务器回的是 `invalid appKey` —— 它读到并解析了我们的认证头，
  只是值不对。这证明 base URL、endpoint 路径、认证头格式、信封解析、
  错误映射全部正确，**唯一缺的就是一个有效的 key 值**。

  `npm run assets:check` 会持续断言「哪些资产真的来自 Lux3D」。
  这不是多余的：原先的判断只看 `.glb` 是否存在，而占位模型写在同样的路径上，
  于是填上 key 之后工具会报「无事可做」并跳过全部 21 个 —— 静默失效，
  而且正好落在刚拿到 key 的人身上。

  降 34% 有效但不足以救回软件渲染。有显卡的机器上不是这样 —— 这一段需要一次
  真实硬件的 F3 读数才能给出可玩的档位建议。
