# 06 · 真实房间里的摆放与异常设计

记录把玩法从"程序化房间"搬到"3DGS 重建房间"时，哪些设计必须改变、为什么。

## 一、家具动不了，所以异常只能是我放进去的东西

程序化房间里，`shift` / `warp` / `twin` 作用在**家具**上：把沙发抬到半空、把床放大三倍、让台灯出现五个。

真实重建房间里这是**做不到的** —— 家具是烘焙进 splat 的像素，我没有它的几何体，无法移动、缩放或复制。

这是一个硬约束，但它导向了一个更自洽的设计：

> **房间是固定的，所有异常都是"多出来的东西"的异常。**

于是七种异常全部作用于我放进房间的物体：

| 类型 | 在重建房间里如何表达 |
| --- | --- |
| `intrude` | 地上多了一个不该有的东西 |
| `stare` | 半空中一个东西正对着你 |
| `shift` | 东西浮在半空 / 粘在天花板上 |
| `warp` | 东西大得离谱 / 小得离谱 / 颜色不对 |
| `twin` | 同一个东西出现了 3–5 个 |
| `invert` | 东西好好地立在原地，但是倒过来的 |
| `swarm` | 同一个东西十几份散落一地 —— 多到数不过来 |

实现上通过 `generateFloor(floor, seed, { foreignOnly: true })`。代价是 `hiddenSlots` 和 `twinSlots` 恒为空（重建房间里没有"原本的家具"可以隐藏或复制），测试里明确断言了这一点。

好处是玩家只要学一条规则：**这个房间里多出来的东西就是异常。**

## 二、锚点必须测量，不能手写

程序化房间的锚点是我手打的，因为墙在哪是我决定的（`catalog.ts` 的 `WALLS`）。

重建房间的墙在采集设备**看到**的地方。手写坐标会把物体放进墙里或者悬在空中。

所以锚点由 `tools/build-anchors.mjs` 从扫描自身的 voxel 场里**测量**出来：

1. 0.25 m 网格扫描，向下射线找表面 → 219 个候选
2. **取众数地面层**（±0.22 m）→ 112 个
   - 向下射线打到的是"第一个实心物"，很可能是桌面、台面 —— 这些必须剔除，否则物体看起来是浮在桌上的
   - 众数层是 −0.40，与出生点实测地面 −0.45 一致
3. **要求行走胶囊真的能站在那**（复用游戏自己的 `resolveCapsule`）→ 97 个
   - 这条最关键：锚点如果玩家到不了，异常就永远找不到
4. 排除出生点 1.6 m 内 → 49 个
   - 睁眼就在手边的道具不是"找"，是跳吓
5. 贪心最远点采样（最小间隔 1.6 m）→ **9 个锚点**

结果：全部落在真实地面（y ≈ −0.4），全部可站立，全部离出生点 ≥1.6 m，分布在约 3 × 8.5 m 的真实房间内部。

`data/room-anchors.json` 是产物，`tests/splatRoom.test.ts` 对这五条性质都有断言 —— 如果扫描数据换了，测试会立刻发现锚点失效。

## 三、标签不能编房间名

程序化房间有"客厅 / 厨房 / 卧室 / 玄关"，因为那是我设计的布局。

重建房间**没有被标注过**。说"厨房里有个东西"是我编的，玩家一旦发现那块地方根本不是厨房，信任就没了。

所以锚点带的是**方位词**（房间中央 / 靠东侧 / 靠北侧…），由锚点相对全部锚点质心的方位算出。测试里有一条明确断言：重建房间的异常标签**不得**出现"客厅/厨房/卧室/玄关"。

## 四、纯数据与渲染器的分离

`src/splat/roomData.ts`（URL、出生点）刻意不导入 `@manycore/aholo-viewer`。

原因：viewer 需要 WebGL，任何导入它的模块在 Node 里都会崩（实测 `TypeError: Cannot read properties of undefined (reading 'bind')` 在 `egs-core` 深处）。摆放逻辑需要出生点和锚点，但不需要渲染器 —— 拆开之后 `tests/splatRoom.test.ts` 才能在 Node 里跑。

同理 `SplatScene.ts` 只是重新导出这些常量，调用方不必知道这个区分。

## 五、房间必须先有"正常"，判断才有对象

第一轮试玩给了一条很直接的反馈：

> 必须要能够轻易分辨这个东西完全就不该出现。

当时做不到，而且是**结构性的做不到**：旁观物件（bystander）和异常是从**同一份荒诞生成目录**里抽的。橡皮鸭、交通锥、地精、宇航员 —— 无辜的和有罪的看起来是同一类东西。于是"这东西该不该在这儿"没有真值，`intrude`（多出来一个东西）这个类型甚至因为无法判断而在重建房间里被整个删掉了。

反馈的第二半（"物件行为的那类挺好"）说明行为类异常是有效的，因为它**不需要参照物** —— 椅子倒挂在天花板上，谁看都知道不对。但同一个房间不能一半靠语义、一半靠行为，因为玩家分不清自己该用哪套判断。

修法是给房间一个**正常**：

| | 用什么 | 判断依据 |
| --- | --- | --- |
| 旁观物件 | 家务家具（盆栽 / 垃圾桶 / 椅子 / 落地灯 / 水壶…） | 什么都不做 = 无辜 |
| `shift` `warp` `twin` `invert` `swarm` `stare` | **同样是**家务家具 | 家具做了家具不该做的事 |
| `intrude` | 生成的怪东西 | 它根本不该存在 |

于是两类判断各自有了唯一答案：**家具永远无辜，`intrude` 永远不是家具**。这两个集合不许相交 —— `foreignPool` 明确排除了 `weirdness: 0`，单测和真机验收各有一条断言盯着它。

### 13 个家务道具是离线生成的 GLB

`tools/build-mundane.py` 用纯 Python 写出 13 个扁平着色的 `.glb`，**一共 83 KB** —— 比原来每个生成资产里的**一张** 2048×2048 贴图还小。全部无贴图，几何是盒子和圆柱。

它们作为 `weirdness: 0` 的条目进入**同一份目录**（`data/foreign-assets.json`），所以走的是同一条已经验证过的 `loadGLTF` 管线，没有新增任何加载代码。

> 一开始我是用运行时的 three.js 建的，结果真机直接报
> `object has attached to another scene, remove it before add to another one`。
> 原因：重建房间的渲染器是 Aholo viewer，它的场景**只收自己的对象** —— `loadGLTF` 返回的正是那种对象，而 three.js 的 `Group` 不是。
> 改成离线 GLB 之后两个问题一起消失：管线复用，且下载量几乎为零。

### 第一关现在教什么

第一关只有 1 个异常，是 `stare`：**一把普通的椅子浮在半空、正对着门口**。

选它是因为它同时满足两件事 —— 不需要任何参照物就能看出不对（所以第一关不需要玩家先学会房间的正常），而漂浮的又偏偏是一把普通椅子（所以第一关同时把"正常"建立起来了）。换成一张恐怖的脸就只剩第一件事。
